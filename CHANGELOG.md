# Changelog

All notable changes to flyw8t. Dates are UTC.

## Unreleased

### Added
- Sign in with a passkey (`/login/passkey`, linked from the sign-in page). No email is typed: the browser offers the passkeys it holds for this console. A passkey that verifies its user counts as both factors, so it signs straight in, past the TOTP code; it does not start sudo mode. The challenge is tied to the browser's sign-in cookie and is spent by the first answer, so an answer relayed from another browser is refused. Keys of disabled accounts, removed keys and counters that go backwards are refused, and every attempt is audited. Security keys registered without a stored passkey cannot be offered and keep working for sudo mode. Migration 0011.
- Where you are signed in: the account page lists your live sessions (browser, address, when signed in, last active), marking any where only the password has been given, and signs out any one of them or every one but this browser. Administrators can sign a user out everywhere from the users table, which also ends the support sessions they started. Every sign-out is audited.
- Sign-in has its own CSRF token: the sign-in page sets a cookie and the form must carry its value, so another site cannot sign a browser in to an account it chose. This adds to the existing `Origin` check.
- Passkeys and security keys (WebAuthn, ES256), and **sudo mode** (ADR-0014 section 3). Each user may register up to 10 from the account page; the first needs the account password, and the current code when two-step verification is on, so a stolen signed-in browser cannot add one. Keys must verify their user (PIN, biometric or device unlock), not only be touched; a signature counter that goes backwards is refused as a possible clone. Sudo mode is a fresh passkey confirmation that lasts 5 minutes for that one session; it is now required to define or archive custom fields, create users, create API tokens, reset someone's second factors, and add or remove passkeys after the first. A password, a TOTP code or a signed-in session never stands in for it. Each ceremony's challenge is spent by the first answer. An administrator's reset also removes the person's passkeys. The two ceremony pages are the console's second use of script (`/static/passkey.js`, same-origin only). Passkeys need the console reached by a host name: browsers refuse them for an IP address, so with an IP-address `FLYW8T_PUBLIC_URL` the pages say why and the server warns at start. Migration 0010.
- Sites as a custom-field level (ADR-0014): a field may allow values per site, between the organization's and the device's, so values now resolve device → site → organization → global → default. Each site has a page (`/sites/{id}`, linked from its organization) listing its devices and its field values, with the same rules for who may set them. A site value meets a "every device must have a value" requirement for the devices in that site. Scripts may read `{{site.key}}`. Migration 0009.
- Script library (ADR-0014 step 2), under **Scripts** for administrators and technicians. A script is PowerShell, Bash or Python, and belongs to one organization or is global; technicians may create and edit global scripts too. Every save is a new revision that is never changed or removed (the database refuses), with its author, a note, a risk class (C0-C3), parameter declarations and a SHA-256 hash of what it would run; saving identical content makes no revision. Each revision shows its diff from the one before, and downloads as a file. The editor is a plain text box (Tab inserts a tab; a file can be loaded into it to review before saving); a save based on an older revision than the latest is refused with the typed text kept. On save the server checks syntax with the language's own parser when installed (PowerShell `Parser.ParseInput`, `bash -n`, Python `compile()`; none of them runs the script), and every view checks parameters (`Name = {{org.key}}`, `"constant"` or `ask`) against the custom fields, flags field placeholders written into the script text, and lists required values missing for fields it reads. `FLYW8T_SCRIPT_CHECKS=off` turns the syntax checks off. New permissions `ViewScripts` and `EditScripts`. Migration 0008. Nothing runs scripts, and nothing is approved, yet.
- Custom fields (ADR-0014 step 1). Administrators define fields: a key scripts will use, a label, a kind (text, number, yes/no, choice or secret), the levels where values may be set (global, organization, device), an optional requirement ("every organization must set its own", or "every device must have a value"), a default, and whether technicians may edit them. Values resolve device → organization → global → default; organization and device pages show each value and where it comes from; every change is kept as history, and clearing a value inherits again. Secret values are encrypted at rest under `FLYW8T_FIELD_KEY` and never shown again. The administration page lists required values that are missing. `/api/v1/devices/{id}` includes the resolved fields (secrets masked). Migration 0007. Nothing runs scripts yet.
- Device management in the console. A device can have a name (the hostname stays what it reports), notes, a site and up to 20 tags; the list searches names, hostnames and tags and filters by tag and by active or retired. A new `ManageDevices` permission (administrators and technicians, within their organizations) covers names, notes, tags and sites; retiring needs `RetireDevices` (administrators). Retiring revokes the credential, closes the connection and hides the device; its history stays. A device never moves between organizations: its history belongs to the one it ran in, so to hand it over, retire it and enroll it again. Migration 0006.
- Changes to many devices at once: tick devices, or take every device the current filter shows, then add or remove a tag, retire, or run a diagnostic on all of them. Running and retiring show every device first and must be confirmed with the exact count; at most 500 devices per change; any device outside the user's organizations refuses the whole change. A run creates one job per device as a **batch** (`/jobs?batch=…`) with live totals; retired devices are skipped. A batch is created all at once or not at all. Retiring a device lets its undelivered jobs expire; a job already running ends with an unknown outcome.
- Running behind Cloudflare Tunnel or a reverse proxy: `FLYW8T_TRUSTED_PROXIES` and `FLYW8T_CLIENT_IP_HEADER` make rate limits and the audit log use each client's real address, believed only from the configured proxies. The Compose file gains an optional `tunnel` profile (cloudflared 2026.9.3, pinned) on a fixed internal network.
- Groundwork for running several server instances on one database (ADR-0009 step 2): job creation and cancel announce work on the `flyw8t_dispatch` channel, and each instance dispatches at once to devices connected to it. A cancel records `last_cancel_sent_at` only when it was actually sent. Attended support and rate limits are still per instance, so run one instance for now.
- Windows release binaries are Authenticode-signed (Azure Artifact Signing) and verified before publishing; a dry-run **Signing check** workflow; `scripts/verify-signature.ps1` for anyone checking a download. Needs the one-time `scripts/setup-signing.ps1` before the next tag.
- Remote control, server side (ADR-0012 step 1): sessions can request `control_input` (new `RunControlSessions` permission). The browser's Allow moves to `awaiting_helper`; downloading the helper (`/s/helper/download`, bound browser only) mints a single-use, 2-minute launch token carried only in the file name. The helper attaches with that token (`/api/support/helper/ws`) and must be allowed in its own window before anything is relayed. In a control session the helper, not the browser, is the technician's media peer, and `connected` needs both of them. Migration 0005. No helper binary yet.
- The remote-control helper, first step (ADR-0012 step 2a): `flyw8t-helper.exe` reads its one-time token and its server from its own file name (`flyw8t-helper-<token>.<server>.exe`; the download now carries the server), shows from which server, who is asking and for which organization in a native dialog with No as the default (text from the server is cleaned of control and invisible characters, and the server line comes first), and answers Allow or Decline. The dialog closes itself if the session ends first; a helper the server cannot introduce ends the session. The server introduces each helper with a `hello` message. No screen or input yet.

### Fixed
- The agent's device key was readable by every user on the machine from `enroll` until `service install` ran (indefinitely, if it never did): `enroll` wrote it into a folder with `%ProgramData%`'s permissions. `enroll` now creates the state folders owned by Administrators and open only to SYSTEM and Administrators, in the same call that creates them, before writing the key, and must run elevated. Re-enroll any device enrolled before this.
- The agent service ran, as SYSTEM, the very file `service install` was run from. Run from a download folder, any account that could write there could replace it and so run code as SYSTEM; on the development machine, four other accounts could. `service install` now copies the agent to Program Files and registers that copy.
- A DLL planted next to the agent (in a download folder, say) was loaded when an administrator ran it: `VCRUNTIME140.dll` and six other imports are not on Windows' KnownDLLs list. The VC runtime is now linked in and the other imports load from System32 only; a planting test that stopped the old build from starting no longer affects the new one.
- Existing folders are checked and refused, never repaired: `enroll` and `service install` refuse a state or program folder (or anything in it) owned by another account, giving other accounts permissions, or holding a junction, link or hard-linked file; the program folder must also hold nothing but the agent. Install also refuses when the service already exists, uses Windows' own known folders instead of `%ProgramFiles%`/`%ProgramData%`, and no longer runs `icacls` (which was looked up next to the agent first, and whose `/C` hid failures). The service accepts only the default state folder.
- The agent service logged nothing: it wrote to standard output, which a service does not have. It now logs to `logs\agent.log` in the state folder (10 MiB, with one rotated file kept), reports a log it cannot open to the Application event log, and is restarted by Windows after it stops itself with an error, not only after a crash.
- A request could be judged by its session as it was when the headers arrived: a client holding a stolen sudo-mode cookie could stall the body and finish it after the session was signed out or sudo mode had ended, and the change was still made. The whole body is now read (within 30 seconds, else 408; within the route's size limit, else 413) before the session is checked, with at most 256 such reads at once and 16 from one address (503 beyond that). Found by the cross-family review (dev-process row 35).
- A device's notes could close the notes box on its page and become markup (Leptos writes a `<textarea>`'s contents without escaping them). Scripts were blocked by the content security policy, but other markup was not. Textarea text is now escaped.
- Remote control review fixes (dev-process row 18): an End the database cannot record still closes every socket of the session at once; no helper credential can be minted or spent once a helper has attached; the browser leaving during the helper step ends the session; the helper download link survives a reload; the final "ended" notice is not lost to a connection reset.
- When an administrator's reset and a technician socket's own sign-in recheck raced to end the same support session, the losing socket could close without the "ended" notice (seen once in Linux CI). It now waits briefly for that notice.

## 0.1.1 — 2026-10-30 (pre-release)

### Added
- The console installs to a phone's home screen as a standalone app (ADR-0011, accepted): web app manifest, regular and maskable icons, an Apple touch icon and a theme colour. `manifest-src 'self'` added to the content security policy. No script and no offline data.

### Fixed
- Review round 4 (dev-process row 16): support sockets end when their technician's account is disabled; the global wrong-code budget refunds only the window a place was taken from; origins are compared in canonical form, so a public URL with `:443` or `:80` works.
- The attended-support security code no longer falls back to "not available" when the browser reports the DTLS certificate a moment after the connection (seen intermittently on Linux CI).
- A device that reconnected while its previous connection was still being set up could lose its new connection to the old one, leaving it on a stale connection. Connections are now ordered by authentication, and the newest always wins (found by Linux CI; this was the protocol-suite flake open since 0.1 development).

## 0.1.0 — 2026-10-30 (pre-release)

First vertical slice. **Not production-ready:** no OIDC or WebAuthn, no signed binaries; two cross-family review rounds on attended support and MFA are fixed, but the second round's fixes are not yet reviewed. See `docs/threat-model.md` § Open items.

### Added
- Decisions (2026-10-30): flyw8t stands alone and will later be a first-class AnchorDesk RMM provider; attended remote control (Phase C) approved (ADR-0010 accepted); mobile administration accepted as a goal (ADR-0011, approach proposed).
- Attended support hardening after cross-family review: only the session's creator can attach (administrators observe and end); sessions belong to an organization; pages stop capture themselves when the server connection is lost, on End, on leaving the page, or when the picker is answered after the end; signaling sealed before an ending commits, with a final notice a full queue cannot drop; `connected` needs both sides; per-socket message limit; race-free per-technician cap; Argon2id-hashed codes and a global wrong-code budget; opening a link spends nothing; one live session per browser; failed attempts, attaches and endings audited by who caused them. Migration 0004.
- Two-step verification (TOTP, RFC 6238), required by default (`FLYW8T_REQUIRE_MFA`): partial sessions until the code is given, session rotation, replay refusal, ten single-use recovery codes, attempt limits, account page, administrator reset. Every existing session is signed out by migration 0003.
- Rust workspace: `flyw8t-protocol`, `flyw8t-domain`, `flyw8t-web`, `flyw8t-server`, `flyw8t-agent`.
- Windows agent: Ed25519 device identity, signed-challenge authentication over WSS, durable job journal (at-most-once execution across duplicates, reconnects and crashes), bounded executor, read-only action catalog (`system.info`, `process.top`, `net.ipconfig`, `net.ping`), periodic inventory, Windows service install with restricted state directory, one process per state directory.
- Server: organizations and sites, enrollment tokens, two-dimension job lifecycle (execution + verification) with `outcome_unknown`, bounded redelivery, deadline sweeper, append-only `job_events` and `audit_events`, roles and organization scoping, bearer-token JSON API with idempotency keys, native TLS, `/healthz` `/readyz` `/metrics`.
- Web console (server-rendered Leptos): overview, devices, device detail with live/cached labelling, jobs with full lifecycle, organizations and enrollment, audit, administration.
- Attended support (browser screen view): pairing code and single-use link, explicit consent, WebRTC between browsers, signaling only after consent, committed security code over the DTLS certificates in use, instant end from either side.
- Tests: unit, exhaustive state-machine, model-based property test, PostgreSQL end-to-end and adversarial protocol tests, native TLS, STD-008 UI capture, two-browser WebRTC run.
- Docs: architecture, threat model, agent protocol, job lifecycle, reliability, monitoring model, AnchorDesk integration, deployment, roadmap, attended support, ADR-0001 to ADR-0010, TLA+ spec (not yet model-checked).

### Fixed
- Linux CI: a support socket cut off for flooding now closes cleanly, so the client always receives the reason (it could be lost to a connection reset).
- Second-round review fixes: the security code is bound to the single transport carrying the shown video; support sockets end when the browser session that opened them is signed out, revoked or rotated; reset and endings decide their transition under the row lock; the global code budget is reserved before work; late asynchronous WebRTC steps cannot act after an ending; socket writes are bounded; turning MFA off rotates the session; the configured public origin is accepted behind a proxy that rewrites `Host`.
- Every console form post from a real browser was refused as cross-origin: `Referrer-Policy: no-referrer` makes browsers send `Origin: null`, which the cross-origin check refuses. The policy is now `same-origin`, and the Chrome test signs in through the real form.
- Two-step verification hardening after cross-family review: factor checks lock the user and the presented session in the same transaction; setting up or turning off the second factor rotates this session and signs out every other; an administrator's reset also ends the user's live support sessions.
