# ADR-0019 · Native WebRTC desktop streaming pipeline

**Status** Proposed for operator review, 2026-11-21. **Scope** Native media design and test fixtures for [issue #53](https://github.com/spilloid/flyw8t/issues/53). The first target is Flyw8t's technician browser. Native technician viewer reuse is a future consumer.

[ADR-0012](ADR-0012-remote-control-helper.md) selects an attended helper, WGC, Media Foundation H.264, WebRTC and a separately authorized reliable, ordered input channel. [ADR-0013](ADR-0013-unattended-access.md) accepts a shared desktop engine under two different endpoint authorities. This proposal specifies how to prove the media pipeline under those decisions. The [research and pinned sources](../research/moonlight-sunshine-streaming.md) describe the alternatives and actual code. The [roadmap](../roadmap.md) still requires Windows and macOS control and Windows UAC/sign-in support for 1.0. [ADR-0018](ADR-0018-attended-elevation-and-persistence.md) remains a proposal.

## Technician experience

From **Devices**, the technician chooses **Remote desktop**, selects the existing console or an identified active user session, and chooses **View** or **Take control**. The browser displays the same desktop that the person at the machine sees. The workstation stays in that login session. A browser-only technician can use this on an enrolled machine behind NAT with RDP disabled. Session sharing here means a technician and local user sharing a desktop, with one authorized remote controller. Inviting another technician would require a separate grant and product decision.

The endpoint shows and enforces the access policy already accepted in ADR-0013. With **Notify with Stop**, a permitted technician can connect to a preauthorized device while its user is away. The user does not have to open a link, launch a helper, read a code or click Allow. A visible banner identifies the technician and offers Stop. **Ask first** waits for a local answer. An unenrolled machine uses the attended helper and its existing consents. The console shows the applicable policy and available actions before connecting. If access is disabled, denied, or the selected session vanishes, it gives that reason and leaves the desktop alone.

Unattended access has an additional identity gate. A person comparing security codes cannot be a prerequisite when the chair is empty. Before enabling this path, prove that the enrolled endpoint can verify the technician session and requested capability against its device policy, resist replay or a substituted peer, and revoke access midstream. A stolen web session or compromised signaling server is part of that review. Enrollment alone grants neither viewing nor control.

## Proposed media path

```text
Selected interactive OS session                       Technician browser
  attended approval OR enrolled-device access policy      authenticated operator
           | scoped, revocable view grant                          |
  approved source -> newest raw frame -> H.264 hardware encoder     |
                                      -> native WebRTC peer =======> video track
                                                   DTLS-SRTP via ICE, direct or TURN
  both peers <-------- existing Flyw8t support WSS: consent, identity, SDP, ICE -------->
  future input sink <====== separately granted ordered data channel on verified peer
```

The server remains the authority for tenant scope, technician session and audited transitions. The endpoint independently enforces the selected OS login, surface, attached peer and the authority for that access mode. The service account and a session number alone cannot identify an approved desktop. Bind to a session incarnation as well as the user and surface so that an ID reused after logout cannot receive stale work. The attended helper runs at the participant's rights. A future agent desktop process would require its own signed endpoint policy, supervisor and per-session authorization. Do not attach a service in Session 0 to whichever desktop becomes active.

**Integration constraint.** On main, `Peers::media_peer` selects the browser participant for view-only sessions and the helper for control sessions. `browser_allow` issues the helper invitation only on the control path. The technician commits its certificate first, then the sharing peer offers the video track. Preserve those roles in the synthetic harness. A shipping view-only native helper would need an explicitly reviewed view-only attach and source-selection contract. Requesting control just to exercise video would widen consent. [Peer routing](../../crates/flyw8t-server/src/support.rs) · [Offer and commitment order](../../crates/flyw8t-web/src/support.js)

1. **Capture.** Prefer WGC for the user-selected window or monitor. Record the frame's monotonic capture time, source dimensions, orientation and geometry generation. Compare DXGI Desktop Duplication only for an explicitly selected entire monitor, on the same adapter and login. On access denial, protected content, session switch or lost output, stop delivery, clear the last image and explain the reason. Require a new grant when the target changes. DXGI can fail on a disconnected session or an inaccessible desktop. Sunshine's WGC service restriction is evidence about that host configuration, not a guarantee about all Windows deployments. [Microsoft Desktop Duplication API](https://learn.microsoft.com/en-us/windows/win32/direct3ddxgi/desktop-dup-api) · [DuplicateOutput failure modes](https://learn.microsoft.com/en-us/windows/win32/api/dxgi1_2/nf-dxgi1_2-idxgioutput1-duplicateoutput)
2. **Encode.** Try a compatible GPU texture path into a hardware Media Foundation H.264 transform, convert to NV12 when required, and measure any staging copy. Negotiate the intersection of encoder and receiver profile/level and packetization mode before sending. Request low-delay operation, avoid B-frame reordering and bound in-flight work. Emit timestamped access units, config and keyframes through WebRTC's H.264 packetizer. Verify SPS/PPS and an independently decodable first/keyframe after resize or loss. A software H.264 path requires an explicit CPU/latency budget and an audited implementation. If none qualifies, report encoder unavailable and offer the existing attended browser flow as a fresh user choice. [Media Foundation H.264](https://learn.microsoft.com/en-us/windows/win32/medfound/h-264-video-encoder) · [H.264 over RTP](https://www.rfc-editor.org/rfc/rfc6184)
3. **Transport and presentation.** Use the WebRTC peer's ICE, DTLS-SRTP, congestion control and pacer. Prefer the selected direct pair where available; use configured TURN when necessary, including TURN/TLS where deployed. Test relay-only by inspecting the nominated pair. TURN sees addresses, traffic volume and timing; endpoints hold the media keys. The console WebSocket remains the consent/signaling path. A media-over-WebSocket fallback would require its own authenticated encryption, capacity budget, review and ADR. The viewer reports ready on a presented frame. Surface one actionable reason while waiting, then clear it on recovery.
4. **Optional formats.** H.264 SDR is the baseline experiment. HEVC/H.265 and AV1 require compatible source, hardware encoder, SDP negotiation **and** a demonstrated receiver decoder. Fall back to negotiated H.264 if either side lacks support. Treat 4:4:4, HDR and ten-bit color as separate compatibility measurements. Optional future audio would use Opus, a separate explicit audio grant, playback permission and a bounded jitter buffer. Today's viewer requests video only and rejects extra media sections or renegotiation. A reviewed protocol revision must constrain any new section and bind every transport to the verified peer. [WebRTC video requirements](https://www.rfc-editor.org/rfc/rfc7742) · [WebRTC audio requirements](https://www.rfc-editor.org/rfc/rfc7874)
5. **Revocation and future input.** Check the technician's committed certificate against the actual DTLS peer and preserve the human comparison code. A displayed code is not evidence that anyone compared it. Refuse native control if the binding cannot be verified. For attended input, require both browser and helper control consent. For enrolled unattended input, require a per-session control grant allowed by endpoint policy. Both paths require the same verified peer throughout the session, an exclusive controller and a live input grant. Allow typed pointer/keyboard events within the selected surface through the OS adapter contemplated by ADR-0012. On Stop, disconnect, revoke, indicator closure or stale lease, invalidate authority locally first. Reject queued events, release locally tracked held keys/buttons exactly once, stop tracks and encoder, and seal signaling. A replacement socket or fresh ICE connection does not reinstate authority. Retain the physical local Stop and test its independence from remote events. Audit actor, tenant, grant, transition and reason; exclude pixels, pressed keys, clipboard, SDP, credentials and candidate addresses from telemetry.

A hostile signaling server can deny service or misrepresent identity. Existing peer checks, endpoint decisions and comparison over an independent channel matter. A compromised server that also serves a modified browser client can subvert that endpoint. TURN encryption does not protect a compromised peer. Scope the “no server media access” test to the designed transport, the tested client builds and their keys; document the residual trust in delivered clients. The optional MCP screenshot path has a separate participant grant and encrypted recipient envelope.

## Proposed Rust interfaces

Signatures describe future ownership boundaries. No workspace crate, wire schema or dependency is added here.

| Trait | Proposed operation | Boundary and failure behavior |
|---|---|---|
| `SessionSupervisor` | `begin_view(authority: ViewAuthority, binding: PeerBinding) -> Result<ViewLease>`, `stop(reason: EndReason)` | Owns session generation, revocation and tasks. The proposed authority identifies either attended approval or an enrolled-device policy grant. The constructor validates policy, organization, technician, peer and exact interactive session/surface. A view lease cannot be converted to an input lease. A later independent control approval can issue a short-lived `InputLease` bound to the same generation. |
| `CaptureSource` | `next(&mut self, view: &ViewLease) -> Result<CapturedFrame>` | A frame carries monotonic time, surface generation, size and a lifetime-bound GPU texture or bounded CPU buffer. Wake blocked waits on Stop. Report access loss, missing display or permission denial explicitly. |
| `VideoEncoder` | `encode(&mut self, frame: CapturedFrame, budget: EncodeBudget) -> Result<EncodedUnit>` | Consumes a frame, returns an access unit with presentation timestamp, keyframe/config metadata and its generation. Never reads the desktop, opens sockets or authorizes input. Cap pending raw frames at one; release a superseded texture immediately. |
| `MediaSession` | `send(&mut self, view: &ViewLease, unit: EncodedUnit) -> Result<()>`, `feedback() -> LinkStats` | Checks the lease and frame generation again at send time. Keep transport and key ownership in the peer. Bound encoder output queues; if loss or overload breaks a dependent chain, discard to the next decodable keyframe and request one. |
| `InputSink` | `apply(&mut self, lease: &InputLease, event: SurfaceEvent) -> Result<()>`, `release_held(&mut self)` | A future adapter can accept surface-relative typed events only after peer/geometry/generation checks. Cleanup is endpoint-owned and idempotent even after the lease expires. No production input implementation in this proof. |

Keep lease constructors private to the endpoint. A serialized role, SDP string or UUID cannot mint a lease. On cancellation, stop accepting work before waiting on OS callbacks; fence every late completion, including the final handoff to the transport. When tearing down, already-transmitted packets may still arrive. The viewer drops its old generation and clears the frame. The [offline Rust test](../research/fixtures/native_stream_probe.rs) exercises the mailbox and stale callback rules in a deterministic single-threaded model. Concurrent driver callbacks, blocked waits and encrypted transport require separate implementation tests.

**Mac interface gate.** Run a per-user ScreenCaptureKit adapter with a selected filter and Screen Recording permission. Measure sample timestamps and pixel formats before fixing the cross-platform frame type. Evaluate a VideoToolbox H.264 encoder separately. Future input requires Accessibility permission and a tested local Stop. Test refusal, revocation, user switching, lock/unlock and sleep/wake on a physical Mac. The existing Swift probe operates on its own window; login-screen behavior and unattended coverage need a demonstrated support contract. [Apple ScreenCaptureKit](https://developer.apple.com/documentation/screencapturekit) · [Repository probe](../../scripts/mac-feasibility.swift)

## Performance experiment

Use motion, scrolling text, a static editor and a full-screen transition at 1920×1080/60 on an identified GPU, driver, OS and browser. Benchmark 5, 10 and 20 Mb/s as starting test points; include a constrained link below the lowest point. Choose the operating bitrate from measured text readability, content, codec and network feedback. Keep the newest raw frame; avoid building latency when the consumer stalls. Honor WebRTC bandwidth estimates, cut bitrate under congestion, then reduce frame rate or resolution if stalls persist. Recover gradually. Count NACK/retransmissions, PLI/keyframes and late drops. Never retransmit indefinitely or silently freeze on a stale frame.

| Metric | Instrumentation | Provisional experimental target |
|---|---|---|
| Encode and queue age | For each numbered synthetic frame, use one sender monotonic clock for acquisition, enqueue, encoder submission and completed access unit. Report queue delay and encode p50/p95 separately, including dropped frames. | Hardware 1080p60 encode p50 ≤8 ms and p95 ≤16.7 ms on the reference machine. Raw mailbox depth ≤1. |
| Capture-to-present | Put frame ID and a changing tile in the test-owned source. Correlate with viewer presentation callbacks. Use a high-speed camera filming both displays or a calibrated common clock with reported uncertainty. A callback alone is not photon time. | LAN 1080p60 p95 ≤100 ms over 5 minutes after warm-up. Report cold time to first presented frame separately and disclose camera refresh/precision. |
| Input-to-photon | In a later approved fixture, film a physical input indicator and the corresponding visible change on the technician display at ≥240 fps. Report p50/p95 over ≥100 trials, sample count and frame quantization. | Provisional LAN p95 ≤150 ms. This PR has no input or hardware measurements. |
| Quality and degraded path | Run identical fixtures on direct and forced TURN paths. Record route type, delivered fps, decoder stalls, jitter, RTT, loss, bitrate and encode/decode time. Vary bandwidth, RTT and burst loss; check fine text at native scale. | For a proposed 50 ms RTT, 1% loss test, first decodable frame within 2 s after a short induced loss burst. Report sustained quality and dropped frames separately per path and browser. |

Run the performance fixture under both attended and device-policy authorization. Record click-to-first-presented-frame and the longest inter-frame gap during scrolling alongside input-to-photon and text readability. Use the same scene, encoder settings, route and browser to make the two modes comparable.

These are hypotheses to test on specified machines, not release claims. Freeze budgets with the operator after collecting repeatable distributions. Keep timestamps within a clock domain unless calibrated. Export aggregates without frame contents. [WebRTC statistics](https://www.w3.org/TR/webrtc-stats/)

## Acceptance and evidence before shipping

| Scenario | Required observation | Where to prove it |
|---|---|---|
| Browser-only unattended takeover | With RDP disabled and no technician desktop app, select an enrolled Windows PC under Notify with Stop. Leave the endpoint untouched during connection. Verify that the browser sees the same numbered test window on its existing console, and technician input changes that window. A person at the PC can Stop immediately. No session creation, lockout or user switch. | Physical PC and separate browser across direct and forced TURN. Repeat under Ask first with no answer, with a view-only technician and after policy revocation. Each must refuse the unauthorized action. |
| Missing, declined, expired or wrong-tenant grant; second technician | No capture, signal relay or input; foreign record remains out of scope. A view-only grant never authorizes control. Audit contains the decision without media content. | Native state-machine and PostgreSQL/socket integration, then two accounts in different organizations. |
| Revoke while connecting and during streaming | Stop before first callback, during encode, and just before send. Late work cannot escape or populate the next grant. Signal loss, process death and reconnect leave the old lease dead. | Offline model for mailbox edges; concurrent native integration and two real hosts for transport. |
| Local Stop and held input | Test button, indicator close and physical Stop with keys/buttons held. Old input queue stays closed; release held state once. A remote event cannot trigger or suppress the physical emergency control. | Synthetic input sink first; later physical keyboard and remote viewer, under separate input approval. |
| Peer mismatch and media privacy | Missing required peer evidence or swapped certificate blocks control. Inspect signaling/TURN traffic and server storage/logs for plaintext media or key material. Repeat with MCP screenshot permission denied. | Instrumented test peers, server audit, relay capture and independent trust review. |
| Browser/interoperability | Current supported Edge, Chrome, Firefox and Safari versions recorded individually. Verify negotiated H.264 profile, first frame, certificate availability, resize, route label and Stop. Unsupported profiles/audio/data channels fail explicitly. | Real browsers and physical decode paths; record which support verified control separately. |
| NAT, firewall and relay | Same LAN, two independent NATs, UDP blocked with reachable TURN/TLS, forced relay, invalid/unreachable TURN, and a signaling-only proxy. Check selected pair, bounded failure and recovery with a fresh grant. | Two hosts plus independently controlled TURN; localhost cannot pass this gate. |
| GPU absent, encoder busy/missing, no HEVC/AV1 decoder | Test known-good H.264, failed hardware initialization and unsupported optional codecs. Approved fallback or clear failure with no unbounded buffering. | Injected errors, integrated and discrete GPU, and software-only or virtual Windows host. |
| Display/session change | Mixed DPI, rotation, display unplug/resize, lock, UAC, switch between console and RDP, disconnect and login replacement. Freeze input on geometry change; user sees an explanation, no cached frame and no switch to a new surface. | Physical Windows desktop plus an independent technician. Secure-desktop/sign-in work stays behind its distinct 1.0 gate. |
| Mac permissions and pacing | Refusal/revocation stops capture, user selection remains scoped, wake requires fresh authorization when the session changes. Record encode and end-to-end metrics above. | Physical supported Mac, versioned browser, explicit permissions and operator-observed Stop. |

## Decisions requested

1. The operator selected the Flyw8t web client and existing-desktop sharing as the product target. Stock Moonlight demand would start a separate ADR and compatibility suite. Define which browser/OS combinations count toward the first release.
2. Approve WGC window capture as the first real-source experiment and DXGI only for an explicitly granted isolated display. Which Windows/GPU, Mac and browser combinations are release reference machines?
3. Confirm direct/configured TURN for this design and assign ownership of TURN/TLS test infrastructure and credentials. A console media relay requires a separate trust and operations decision.
4. Select the minimum usable fallback on machines with no qualifying hardware H.264 encoder. Approve performance budgets only after the hardware reports. Decide future audio scope and exclusive-control policy before changing topology.

The next reviewable implementation should stop at a test-only synthetic H.264 peer proving browser decode and authenticated cancellation. Only after that succeeds should a local test-owned desktop enter the experiment. Production remote control, elevation, installation and unattended policy remain separate release work.
